We shipped at 14:20 on a Tuesday. By 14:23 the on-call channel had eleven messages in it and someone had already asked whether we should roll back.

The deploy was one migration. Six lines. It added a boolean column to `users` with a default of `false`, because we were rolling out a feature flag per account and that seemed like the obvious place to put it.

```ruby
class AddOnboardingCompleteToUsers < ActiveRecord::Migration[6.1]
  def change
    add_column :users, :onboarding_complete, :boolean, default: false, null: false
  end
end
```

I had run it locally against a seed database with about four hundred users. It took 30 milliseconds. Production had 4.2 million users, and for nine minutes nobody could log in.

## What I thought was happening

My first theory was that the column write itself was the problem. Four million rows, each one needs a `false` written into it, that's real work — of course it's slow.

That theory was wrong, and it wasted the first four minutes. We were on Postgres 13, and since Postgres 11, adding a column with a constant default doesn't rewrite the table at all. It writes the default into the catalog and materializes it lazily as rows get updated. The `ALTER TABLE` itself is nearly instant regardless of table size.

So the write wasn't slow. Something else was.

## What was actually happening

`ALTER TABLE` needs an `ACCESS EXCLUSIVE` lock. That's the strongest lock Postgres has, and it conflicts with everything, including the plain `SELECT`s that our login path was running.

Here's the part I didn't understand at the time: Postgres locks queue, and the queue blocks behind itself.

There was a long-running read on `users` when the migration started. Some analytics query, forty seconds of sequential scan, entirely harmless on its own. The migration asked for `ACCESS EXCLUSIVE`, couldn't get it, and got in line behind that query.

And then every request that arrived after the migration got in line behind *the migration*.

That's the bit that turns a slow query into an outage. A pending `ACCESS EXCLUSIVE` lock doesn't politely let reads through while it waits. It's ahead of them in the queue, so they wait too. One forty-second analytics query plus one instant migration produced nine minutes of downtime, because by the time the queue drained there were thousands of connection-starved requests piled up behind it and the connection pool had long since given up.

You can watch this happen, which I did, from a psql session, feeling useless:

```sql
SELECT
  a.pid,
  a.wait_event_type,
  a.state,
  now() - a.query_start AS duration,
  left(a.query, 60) AS query
FROM pg_stat_activity a
WHERE a.datname = current_database()
ORDER BY a.query_start;
```

The output was one `idle in transaction` analytics query at the top, an `ALTER TABLE` in `Lock` wait below it, and then several hundred `SELECT ... FROM users WHERE id = $1` rows underneath, all of them waiting on a lock they had no logical reason to care about.

## The fix, which is smaller than it should be

The real fix is one line. Don't let a migration wait in line:

```ruby
class AddOnboardingCompleteToUsers < ActiveRecord::Migration[6.1]
  def up
    execute "SET lock_timeout = '3s'"
    add_column :users, :onboarding_complete, :boolean, default: false, null: false
  end

  def down
    remove_column :users, :onboarding_complete
  end
end
```

With `lock_timeout` set, the migration tries to acquire the lock, fails after three seconds, and raises. The deploy goes red. Nobody's login breaks. You look at what's holding the lock, kill it or wait for it, and run the migration again.

A failed deploy is a mildly annoying afternoon. Nine minutes of downtime is a postmortem, an apology email, and a meeting where someone asks whether migrations should require a second approver.

I now think of `lock_timeout` as the migration equivalent of a seatbelt: it does nothing at all on the vast majority of trips, and the one time it matters you'd trade a lot to have it on.

## The rest of what we changed

We put [strong_migrations](https://github.com/ankane/strong_migrations) in the Gemfile that week. It's a linter for migrations that fails the build on patterns that take dangerous locks, and it explains the safe alternative in the error message rather than just saying no. It would have caught the original migration, though not for the reason I expected — it flags a whole category of operations I hadn't thought about, like adding an index without `CONCURRENTLY` and changing a column type in place.

We also stopped running analytics against the primary. That one was less about the incident and more that the incident gave us the leverage to finally do it.

And we added the lock query above to a dashboard, because the difference between "the database is slow" and "something is holding a lock" is about eight minutes of guessing when you're under pressure and can't remember the name of the view.

## What I'd tell myself in 2019

Test migrations against row counts you'll actually see, but understand that row count wasn't the variable that mattered here. A table with four million rows and no concurrent traffic would have been fine. A table with four hundred rows and one long-running read would have produced the same outage.

The variable that mattered was *traffic*, and my local database had none.

That's the general shape of the lesson, and it's not really about Postgres. Local environments are quiet. Almost everything that has bitten me in production has been a concurrency problem that a quiet environment structurally cannot show you — a lock, a race, a job running twice, two requests interleaving in an order I hadn't pictured.

I don't have a clean solution to that. I just try to ask, before anything touches a hot table, "what happens if this runs while the site is busy?" It's a low bar. It would have caught this one.
