A user emailed support to say they'd received the same "your report is ready" notification 118 times. They were polite about it, which somehow made it worse.

By the time I looked, Sidekiq had processed the job 40,312 times in about four hours. The queue depth graph looked like a wall.

## The job

Nothing about it is unusual. This is roughly it, with the names changed:

```ruby
class ReportDeliveryJob
  include Sidekiq::Job
  sidekiq_options retry: 25

  def perform(report_id)
    report = Report.find(report_id)
    file = ReportRenderer.new(report).to_pdf
    upload = S3Uploader.upload(file, key: report.storage_key)
    report.update!(delivered_at: Time.current, url: upload.public_url)
    ReportMailer.ready(report).deliver_now
  end
end
```

Read it as an engineer looking for a bug and you probably won't find one. Read it as a list of things that can fail halfway through and it gets more interesting.

## Two bugs, one symptom

The first bug was in how the job got enqueued.

```ruby
Report.transaction do
  report = Report.create!(user: user, params: params)
  ReportDeliveryJob.perform_async(report.id)
end
```

Sidekiq stores jobs in Redis. Redis is not in your Postgres transaction. So `perform_async` hands the job to Redis immediately, a worker picks it up in a few milliseconds, and calls `Report.find(report_id)` for a row that hasn't been committed yet.

`ActiveRecord::RecordNotFound`. Sidekiq catches it, counts it as a failure, and schedules a retry.

On its own that's self-healing. The transaction commits, the retry succeeds, and you'd only notice it as a bit of noise in your error tracker. We had that noise for months. I'd looked at it, decided it was benign, and moved on. It was benign, right up until it wasn't.

The second bug is the one that turned noise into 40,000 emails.

`ReportRenderer` had started timing out on large reports. Not always — it depended on how much data the report covered. So the sequence became: render succeeds after 90 seconds of work, upload to S3 succeeds, `report.update!` succeeds, and then `deliver_now` hits an SMTP timeout because our mail provider was having a slow afternoon.

Sidekiq sees an exception. Sidekiq retries the whole job.

Which re-renders the PDF, re-uploads it, re-updates the row, and tries the email again. Every retry sent an email if SMTP happened to be healthy that second, and re-did 90 seconds of rendering work whether it was or not. Twenty-five retries per job, several hundred reports in flight, exponential backoff that had barely started spreading them out yet.

The rendering load slowed the workers. Slow workers made SMTP timeouts more likely. More timeouts meant more retries. It fed itself.

## What I got wrong in the first hour

I turned retries off. `sidekiq_options retry: false`, deploy, done.

That stopped the emails and it was the right call at 11pm. But I described it to myself as a fix, and it isn't one — it just converts "does the wrong thing repeatedly" into "silently drops work". A week later we'd have found reports that never got delivered at all and no record of why.

The actual problem isn't that the job retried. Retrying is correct. Sidekiq's whole delivery model is at-least-once, and any distributed queue worth using makes that same promise, because the alternative is losing work. Your job will run more than once. That's not an edge case to handle, it's the contract.

The problem was that the job wasn't safe to run twice.

## Making it safe to run twice

Three changes, roughly in order of how much they mattered.

**Enqueue after commit, not inside it.** Rails has this built in and I just wasn't using it:

```ruby
class Report < ApplicationRecord
  after_create_commit -> { ReportDeliveryJob.perform_async(id) }
end
```

`after_create_commit` fires once the transaction has actually committed, so the row exists by the time a worker looks for it. If you're enqueueing from a service object instead of a callback, `ActiveRecord.after_all_transactions_commit` does the same thing without pushing logic into the model.

**Split the job at the failure boundaries.** Rendering, uploading, and emailing fail for unrelated reasons and cost wildly different amounts to redo. Bundling them means the cheapest step's failure re-triggers the most expensive step's work.

```ruby
class ReportDeliveryJob
  include Sidekiq::Job

  def perform(report_id)
    report = Report.find(report_id)
    return if report.delivered_at?

    unless report.url
      file = ReportRenderer.new(report).to_pdf
      upload = S3Uploader.upload(file, key: report.storage_key)
      report.update!(url: upload.public_url)
    end

    ReportMailer.ready(report).deliver_now
    report.update!(delivered_at: Time.current)
  end
end
```

Now a retry after an SMTP failure skips the 90 seconds of rendering, because `report.url` is already set. And a retry after the whole thing succeeded does nothing at all, because `delivered_at` is set.

**Guard the email specifically.** The `delivered_at` check above still has a gap: two workers running the same job concurrently can both pass the check before either writes. Narrow, but 40,000 executions will find a narrow window. A unique index turns the race into a constraint violation, which is a much better problem to have:

```ruby
# db/migrate/..._create_report_deliveries.rb
add_index :report_deliveries, %i[report_id kind], unique: true

# in the job
ReportDelivery.create!(report: report, kind: "ready_email")
ReportMailer.ready(report).deliver_now
rescue ActiveRecord::RecordNotUnique
  # Another worker already sent this one.
  nil
```

The database is the only thing in the system that can actually arbitrate "has this happened yet", so let it.

## The thing worth taking away

I'd internalized "jobs should be idempotent" as advice. I could have recited it. I'd probably have said it in an interview.

What I hadn't internalized was that it's not advice, it's a consequence of how the queue works, and it applies to *every* job I write, including the boring ones. There is no such thing as a job that runs exactly once. There's only "safe to run twice" and "hasn't run twice yet".

The other thing: that `RecordNotFound` noise had been in the error tracker for months, and I'd triaged it as benign. It was benign. It was also a bug in the enqueue path that had been sitting there waiting for a second bug to show up and make it expensive.

I'm now much more suspicious of errors I've decided to tolerate. Not because tolerable errors are secretly catastrophic — most of them really are fine — but because "I understand why this happens and it's harmless" and "I understand what this looks like when something else goes wrong at the same time" are different amounts of understanding, and I'd confused them.
