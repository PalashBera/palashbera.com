Most of the prototypes I've built have ended up in production. I used to think that was a compliment about the prototypes. I've come to think it's mostly a fact about organisations: if a demo works and someone senior liked it, it is going to ship, and the only real question is whether you get to decide what happens next or whether it happens to you.

So I've stopped writing prototypes as though they're disposable. Not because they aren't — most of the code genuinely should be thrown away — but because the parts that survive are never the parts I'd have guessed.

Here's what I actually do differently now.

## The demo is a hypothesis, and it isn't about the code

A proof of concept exists to answer one question, and it's worth writing that question down before starting, because the answer usually isn't technical.

"Can we generate these reports automatically?" is almost never really asking whether report generation is possible. It's asking whether the output is good enough that a human will stop doing it by hand. Those need different demos. The first one you can satisfy with a script. The second one requires showing it to the person whose job it is and watching their face.

I've built the technically-impressive version of the wrong question more than once. It demos beautifully and then quietly dies, and the reason it dies is that nobody's behaviour changed.

## Fake the parts that are only expensive, build the parts that are risky

This is the one that took me longest to learn, and I had it backwards for years.

The instinct is to build the easy parts properly and hand-wave the hard parts. It feels productive. You get something on screen quickly. But it means the demo proves the thing nobody doubted and skips the thing that will kill the project.

So now I ask which part I'm least sure about, and I build only that, as crudely as possible. Everything else is hardcoded.

On one project the risky part was whether we could reconcile two systems whose IDs didn't match — no shared key, just names and dates that mostly agreed. That was the whole project. The UI was irrelevant. So the prototype was a Python script that printed a match rate to the terminal, and the "demo" was a spreadsheet of the 6% it couldn't match, which we went through line by line with someone who knew the domain.

That project shipped. The reconciliation logic from that script is essentially still what runs in production, because it was the part that got real scrutiny early.

Conversely: if the risky part is "will people use this", build a clickable thing with fake data and no backend at all. Don't build a schema. You'll get the schema wrong anyway, because you don't know what the workflow is yet.

## Write down what you skipped, while you're skipping it

I keep a section at the bottom of the PR description or the README called "not real yet". It takes a minute per entry and it's the single highest-leverage habit I have.

```markdown
## Not real yet

- Auth is a hardcoded user ID (`app/services/current_user.rb:12`).
- No pagination. Breaks somewhere past ~2k rows, untested past 500.
- Rate limits on the vendor API are unknown; we've only ever
  called it 30x/hour.
- Timezone handling assumes everything is IST. Definitely wrong
  for the Singapore team.
- The retry in `SyncJob` isn't idempotent. Will double-write if
  it fires twice.
```

Two things make this valuable, and neither is what I expected.

The obvious one is that it becomes the hardening backlog. When the project gets a green light, the estimate is mostly written already, and it's specific enough that someone else could pick it up.

The less obvious one is that it changes the conversation about timelines. "It's basically done, just needs polish" is how prototypes become production by accident, and it's not a lie exactly — the demo does work. But a list of eleven specific gaps, with file references, is very hard to argue with. I've had a stakeholder read that list and reprioritise on the spot, which is a much better outcome than me privately knowing it wasn't ready.

Write it as you go. Reconstructing it later doesn't work, because the things you cut are invisible once you've stopped thinking about them.

## Real data, early, even when it's inconvenient

Synthetic data is uniformly shaped. Real data has a customer whose name is 400 characters of pasted HTML, a date in 1900 that means "unknown", two rows that are the same record entered twice with different capitalisation, and a nullable column that is null 94% of the time and load-bearing the other 6%.

Every prototype I've built on clean fixtures has had a rough production week. Every one where I pulled a sanitised extract on day two has been boring to ship.

You don't need much. A few thousand real rows is enough to find the shape problems, and it's enough to notice that the query you were proud of does a sequential scan when the data isn't perfectly distributed.

## The four things I harden first

When a prototype gets promoted, this is roughly my order, and it's ordered by "what will hurt in week one", not by what's most interesting:

1. **Authorization.** Prototypes usually have authentication of some kind, because you need to log in to demo it. They rarely have authorization, because during the demo you're the only user and everything is yours. This is the gap that turns into an incident, and it's almost never a missing check on the obvious page — it's the JSON endpoint the frontend calls, which nobody thought of as a page at all.

2. **The thing that runs on a schedule.** Anything asynchronous in a prototype has been run by hand, by me, watching it. Once it runs on a cron it will overlap with itself, fail at 3am, and retry. See also: everything I learned from a job that ran 40,000 times.

3. **Whatever the demo did exactly once.** Uploads, exports, external API calls. These are fine at one per demo and interesting at a thousand per hour. Find the concurrency limit before it finds you.

4. **Observability, but only enough to answer "is it working".** Not a dashboard. One log line per meaningful operation with an ID you can grep, and an alert on the queue backing up. That's genuinely enough for the first month, and building more before you know the failure modes means instrumenting the wrong things.

Notably absent: test coverage as a number, refactoring for elegance, and performance work. Those matter, but they're week three. Nothing in week one goes wrong because a method was too long.

## The awkward part

The honest version of all this is that a prototype's job is to be convincing, and a production system's job is to be correct, and those goals are not just different but sometimes opposed. The most convincing demo is the one with no error handling, because error handling is invisible when nothing goes wrong and it costs you the time you could have spent on the thing people will actually look at.

I don't think there's a way around that tension. What I've found is that you can be deliberate about which side you're on, and say so out loud. "This is a prototype, here is the question it answers, here are the eleven things that aren't real" is a sentence that has never once gotten me in trouble.

"It's basically done" has.
